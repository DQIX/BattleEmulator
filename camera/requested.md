1. **`row+4` はactorの意味状態ではなく、未初期化stack scratch。ただしROMはそのzero/nonzeroを実際の処理入力に使う。** `021E1958` が12-byte work rowへ書くのは `row+0=actor ID`、`row+1=presentation class`、`row+8=presentation object pointer`だけで、`row+4`には一度も書かない。callerの`021E08BC`はframe確保後の`sp+0x15C`をrow bufferとして使うが事前zero-clearしない。さらに直前の`021E05F0`はframe総量`0x100`・row buffer=`sp+0x4C`、`021E08BC`はframe総量`0x210`・row buffer=`sp+0x15C`で、**caller SP基準では両方とも同じ`SP-0xB4`**を踏む。したがって`021DC9CC → 021E05F0 → 021E08BC`では、05F0のscratchを08BCがそのまま再利用する。`021E2904`だけは必要なrowの`+4`へ明示的に`1`を書くため、「完全なランダムゴミ」でもなく、**stack residue＋局所write**として理解する必要がある。`021E1A1C`は`row+4`を書かない。
   　turn開始時にはfresh ROMでphysical prefixが実際に`[nonzero, nonzero, zero, zero]`、生値では`[0x027E3488, 2, 0, 0]`として再現し、turn2先頭でも同じ`1100`が再現した。一方、「前turnの抽象stateをそのまま永久保持すればよい」という初期修正は撤回されている。battle-entry側では`0216280C → 02032B14 → 02035488 → 0207F5FC → 020B5D38 → 020B5B34/5AEC → 020B7224`までstack producer familyを追跡済み。ただし`020B7708`のloop counter=`2`そのものがC0の`row+4=2`へ直接対応する、という強い解釈までは証明されていない。現在の有効な理解は「turn境界/戦闘開始側のstack footprintが1100を再形成する」であって、「意味状態の持ち越し」ではない。
   　同様に、特定setupで`TTTT`が観測された事実自体は消してはいけない。ただし「type22 action終了後なら常にTTTTを再注入」と意味化するのは粗すぎる。実ROMでは後続DQ9 10 setupで`TTTF`まで変化しており、`021D94F0`のような深いstack frameを含むaction間処理が同じscratch帯を上書きできる。つまり観測値は正しいが、不変なaction属性ではない。

2. **`[0x02392920, 0x02392920, 8, 15]` の正体はHUD/text rendererのstack footprint。** 最終writer群は`0x0204F2xx`帯へ収束し、直接producerは`FUN_0204F284 → FUN_0204F2F8`。`0204F2C8`等でglyph系引数をstackへ積み、`0204F2E8`では描画nibble系値を置き、`F2F8`入口の`stmdb sp!,{r4,...,r11,lr}`がcallee-saved registerをspillする。各`F284` callsiteは`mov r0,r10 → bl FUN_0204F284`、`F284`内部は`mov r7,r0`なので、観測先頭2wordはsaved `r7` / saved `r10`として同じrenderer context pointer `0x02392920`になる。`8`はglyph width、`15`は4-bit描画値。
   　exact footprintを作るcallsiteはさらに`FUN_02050678`内`0x02050BD0`まで絞れており、その時の`FUN_0204F284(..., param5=8, param6=0xF0, param7=0x0F)`も取得済み。上位の動的chainは`020515EC → 02051880 → 02050678 → 02050BD0 → 0204F284/F2F8`。描画対象byte列はCP932の「／」で、`X／Y`系HUD文字列まで追えている。したがって「ためる固有値」「929固有値」「カメラ方角乱数4個」という意味付けは誤りで、**たまたま後の`021E08BC` row scratchと同じstack帯へ残ったrenderer ABI footprint**である。

3. **free-cameraの方角RNGは上のrenderer residueとは別系統。** `FUN_overlay_d_00__0216FDA4`は実際に`RandInt(rng,100)`、retry gate用`RandInt(rng,5-retryCounter)`、4方向選択`RandInt(rng,4)`、条件付き`getFloatRand()`を消費する。4 camera vectorは`0x02184370`側のtableを選ぶ。つまり「free-camera orientationがRNG依存」は正しいが、`[ptr,ptr,8,15]`をその乱数値と解釈するのが誤り。`0204F284/F2F8`自身には`RandInt/getFloatRand`呼出しがない。

4. **`021E2664` は敵との距離計算ではなく、presentation gridの混雑退避処理。** 9×9 gridで現在nodeの6近傍を列挙し、各候補についてさらに周囲6近傍の空き数を数え、最も空きの多いnodeへactorを逃がす。旧占有を消し、新nodeを設定する処理まで同関数内。`row+4 != 0`経路では通常の「近傍数が十分なら動かない」というearly-return条件を実質バイパスするため、候補があれば退避が強制される。関数引数はroster rowと81-node work gridで、target ID/target座標を直接受け取らないので、`021E2664`自身には「敵とのユークリッド距離」を判定する能力はない。

5. **ただし別経路に、本物のproximity conflict判定がある。** `021E08BC`内でDQ9 action ID `9..11`かつcurrent actor flag `0x80`のとき、`021E2850`のmovement eligibility判定**より前**に処理される。current actor→targetの**battle-world 3D線分**と各presentation node点を`02030FA0`へ渡し、point-to-segment距離が`<0x1800`のnodeだけを`021E2904`へ渡して`0xFF` marker化する。実ROM action10では`021E2904`が同setup中に2回呼ばれ、LRは`021E0C5C`、観測node集合は`[22,30,31,40]`と`[30,31,40,48,49]`。C++はこの処理をeligibility後にしか持っていなかったため、flag 0x80でeligible=falseになるactorのmarkerを丸ごと欠落させていた。既存`021E1FD8 → 021E2904`は別xrefなので残す必要がある。
   　occupancyについても「全mapをsetup間でそのまま永続化すればよい」は広すぎて撤回された。`021E1A1C`には既存`0xFF` markerを残しつつ他を再構築する性質があるが、今回必要だった本質は上記の**pre-eligibility producerを正しいタイミングで走らせること**。全FFを無差別保持すると別action由来markerまで残って配置を変えてしまう。さらに一時疑われたAI depth fieldも、Ghidraの`ushort* +0xA4`はbyte offsetでは`+0x148`なので既存minerが正しかった。depth=`1`、maximumLayer=`3`、recursive paint式も正しく、候補差の原因はpaint algorithmではなく**paintへ渡すoccupancy input**だった。

6. **presentation周辺には最低3種類の座標状態があり、混同するとnearest node・conflict・後続cameraが全部ずれる。** 現在のpresentation/node worldはpresentation object `+0x10/+0x14/+0x18`、battle actor physical worldはactor本体 `+0x44/+0x48/+0x4C`、base battle-worldはpresentation object `+0x04/+0x08/+0x0C`側。`FUN_021E1E50`のnearest-node計算が実際に読むのはpresentation worldではなく、`read_data_limit_e9_1(actorId)`で得た**battle actor本体の+0x44/+0x4C**。Heroでpresentation側が `(10641,18432)`のままでもbattle actorが `(0,10240)`になり、`021E1E50`がnode48を返す実測がある。
   　BACT opcode `0x4F mode0`の復元経路は`021E71A4 → 021695A8 → 全actorへ0204AB8C → 02049B10 → base world読出し → 02013920(actor+0x44, baseWorld)`。実測Heroはbattle-world `(0,18432)`からbase `(0,10240)`へ戻り、敵も各base位置へ復帰する。つまり「route endpointへpresentationとbattleを常時同期」は不正確。`0216F62C`のclampもbattle actor座標側で、presentation worldとは別。

7. **turn-endにはglobal formation recenterが実在する。** overlay26 `FUN_overlay_d_26__021D9434`が全participant nodeを9×9 row/columnへ分解し、全体が一方向の外縁へ寄っている場合に共通shiftを計算する。callsite `021D9AEC → 0204A1B0`はpresentation start node更新、後段`021D9B34 → 0204A9F4`はpresentation/node world更新。移動後全nodeが0..80内へ収まる場合だけ全員まとめて動かす。
   　call stackは`0x02161FE8 → 0x021D9434 → 0x021D9AEC`。main側`FUN_02161D9C`でbattle phase/state `+0xE24 == 7`かつ`FUN_020A3D20()==3`のとき呼ばれるため、action固有処理ではなく**turn-end global presentation maintenance**と確定している。従ってC++でも各`CompleteActionPresentation()`ではなく、全action終了後に1回だけ入れるべき処理。

8. **`camera.bin`はoverlay codeの正本にしてはいけない。** 当時開いていたものはRAM dumpで、live overlay26と同一アドレスの命令が一致しない例が確認された。`overlay_jp.js`が読むloaded-overlay table `0x01FFD384...`から、現在slot3=`overlay ID 26`、start=`0x021D9300`を同定。live `0x021D9AEC`はARM `BL 0x0204A1B0`だったが、camera.binの同アドレスは別命令だった。よってoverlay関数のcaller解析はlive codeまたは正しいoverlay26 binaryを使う。
   　overlay監視自体は`0x01FFD384..0x01FFD389`へのwrite breakpointへ整理され、固定loader PC依存を避けられることも確認済み。

9. **presentation goal setupは全actionで走らない。** ROMの`FUN_02163F68`はactdata record `+0x14`のhigh nibbleが`2`または`5`のときだけ`021E08BC` setupを許可する。これは既存generatorが`targetScopeCode = word14 >>> 28`としてROMから採掘済みで、`TargetScope::single / single_formation`に対応する。scope 4などでは既存goalを壊さず、必要なroute再計画だけ行うべき。`021DC9CC / 021E08BC / 02163F68 / 021DC1D4 / 0204A264`を同時decompileして確認されている。

10. **action record履歴とgoal setup有無は独立。** ROMではgoal setupを通らないactionにも0x28-byte presentation action recordが存在する。C++では`hasPresentationSetup`時だけ`CommitActionProgressRaw()`を呼んでいたため、最初の非setup actionで履歴が途切れ、その後も`presentationActionRecordIndex=-1 / hasPreviousAction=false`となってlater actionをfirst-action相当に扱っていた。各real actionについてrecord historyを1回進め、mapped presentation setupの有無とは分離する必要がある。
    　synthetic action 944もROM側に実recordとして入る。実際3-turn同期ではROM/C++双方で944が入り、履歴・RNGとも一致した。

11. **target cacheには個別goal setupより前のrecord-pool pre-passがある。** 実機で`0204A278(C2,C1)`へ停止し、直接caller=`021E05C8`、所属関数=`021E050C`、さらに上位caller=`021DBFD0`まで取れている。`021E050C`はturn/action preparationで**構築済み0x28-byte presentation action-record poolとsnapshot chain**を走査し、各snapshot actorのpresentation `+0x4C cachedTargetId`へrecord targetを書き込む。単純なcombat action配列をなぞる処理ではない。
    　実行順は`021DBFD0 → 021E050C`が先、その後各action直前に`021DC9CC → 021E05F0 → 021E08BC`。さらにgoal assignment側の`021E1FD8 → 0204A278`も別用途で存在するので消してはいけない。`0216AF7C`にも`0204A278` callerはあるがactor ID 0..3の味方枠だけで、敵C2 stale cacheの一般解ではない。

12. **future participantのgoalは計算しただけでstartへ無条件commitしてはいけない。** C++の`CompleteActionPresentation()`が`actorId/actionIndex`を捨てて`CommitAllCurrentRouteEnds()`していたのはROM反例と衝突する。ROMではfuture goalだけ先に作り、後続actionまで`start != goal`のまま保持するケースがある。current actor側は別途`CommitActionProgressRaw()`等で進むため、全actor一括commitは強すぎる。
    　同じ理由で「action BACTが終わったら非actor routeも全部endpointへ進める」という一般化も危険。future/nonactor progressionにはcurrent actor route状態など追加条件があり、producer stateを追う必要がある。

13. **battle-worldをpresentation-worldへ進める処理自体は存在するが、無条件ではない。** fresh比較ではcurrent actorに実routeがあるTurn3では次setupまでにbattleWorldがpresentation側へ進む。一方Turn4 action0はcurrent actor route count=`0`で、ROM battleWorldはbase側のまま。このため「通常攻撃なら必ず同期」でも「action終了なら全員同期」でもない。

14. **`0x4F`実行有無をselector sourceから推定してはいけない。ここは独立したBACT-resource state。** DQ9 73はselector callerが`0x021DC8C8 = direct membership`なのに、その後`0x4F mode0`を実行する。一方DQ9 155は静的action BACTに0x4Fを持っていてもliveで実行しない反例。したがって過去の「`TriggerSource::action_bact`なら0x4F」という一般化は破綻している。
    　ROM側ではselectorとは別に後段BACT interpreter `021E9C0C`があり、controller `stateE28==3`時に`021DCE88`から呼ばれる。一方SP-BACT selector caller `021DCF8C`は別の`stateE28==4`。さらに`021DC70C`はdirect membershipが見つかると、そのactor-resource側presentation treeをselectorと後段state3へ渡す。つまり重要なのは**実際に選択されたmembership/action/fallback resource groupの中身**。
    　従来8-byte `MembershipCell`は`selectorProjection/count/trackingCount`だけで64bitを使い切り、resource group内の`0x4F mode mask`を捨てていた。そこで12-byte schema v4へ拡張し、selected groupのmaskをruntime decisionへ渡す。ROM固定データでは今回C0の`profile347 z040c.mon / action73` groupが`0x4F mask=0x01`、155を直接membershipで持つ4 profileは全て`mask=0x00`。これによりaction ID特例なしで73/155を分離でき、Turn4のmode0後Hero battleWorldと次setupのC0/C2 goalがROM値へ戻った。

15. **free-cameraを`action ID → 1個のbehavior`へ潰す設計はlossy。** action161はdirect selector suppressed=true、direct tracking RNG=0だがmembership nontracking sourceが8。action231はdirect BACT自体がないのにmembership側にtracking source 6＋nontracking source 2を持つ。したがって旧`trackingCameraActions={63,65,231}`のような分類ではresource/profileによる差を表現できない。
    　generator/runtimeでは`direct selector suppression`、`direct tracking count`、`actor membership`、`action BACT`、`fallback membership`を独立factとして保持すべき。`TrackingCameraFor()`もactor membership→action BACT→fallback membershipというresource selectionを行うため、後続処理はaction ID名ではなく**選ばれたcell/group**を見る必要がある。selector suppression自体は正しくても、誤ったrouteやgoal stateを与えたためselectorが発火したケースも多く、「selector例外を足す」よりproducer state修正が原則。
